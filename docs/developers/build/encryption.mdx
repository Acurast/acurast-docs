Every Deployment holds its own encryption keys on each Processor it runs on. The private keys never leave the Processor. A Deployment uses them to exchange encrypted messages with its backend, with the account that created it, or with other Deployments:

| Runtime | Encrypt | Decrypt |
|---|---|---|
| [Node.js](/developers/build/nodejs-runtime-environment#signers) | `_STD_.signers.<curve>.encryptFor(publicKey, payload, salt?)` | `_STD_.signers.<curve>.decryptFrom(publicKey, envelope)` |
| [Cargo](/developers/build/cargo-runtime-environment#signer) | `signer_encryptFor` | `signer_decryptFrom` |

## Keys

Each Processor gives a Deployment a `secp256k1` encryption key and, where its keystore supports key agreement (requires Android 12 or later), a P-256 encryption key. P-256 is `secp256r1` in `_STD_.signers` and `p256` everywhere else: in the Node.js key listings (`getEncryptionKeys()`, and `encP256` in `getAssignedProcessors`) and in Cargo. `_STD_.job.getEncryptionKeys()` in Node.js and `deployment_encryptionKeys` in Cargo return the keys that exist on the current Processor. The `secp256k1` encryption key is the Deployment's `secp256k1` signing key.

For every assignment, a Processor publishes the Deployment's public keys on-chain: the signing keys and one encryption key, `encP256` where P-256 is available and `encSecp256k1` otherwise. `_STD_.job.getAssignedProcessors(success, error)` and `deployment_assignedProcessors` read them. Encrypt with the curve of the key you use, and have the Deployment use the matching signer.

All public keys used for encryption are 33-byte compressed points (hex, starting with `02` or `03`). Keys in any other encoding are rejected.

## Trusting keys

Every guarantee on this page assumes the public keys in use are the right ones.

- **The Deployment's keys.** Take the keys each assigned Processor published for the assignment from the chain, read through a node or light client you trust. Accept envelopes only from those keys, and check any key that reaches you over the network against them. Never accept a Deployment key from an unauthenticated channel, such as a request the Deployment sends to its backend: anyone on that path can swap in their own key.
- **The peer's key.** The Deployment takes its peer's public key from its own code or from its [encrypted environment variables](/developers/build/environment-variables), never from an unauthenticated channel.
- **Keys outlive an App version.** A [mutable Deployment](/developers/tools/cli#updating-mutable-deployments) keeps its keys when its App is updated, and `reuseKeysFrom` carries keys over to a new Deployment. Every later App holding the keys can read earlier envelopes and send as the Deployment, so trusting a key means trusting whoever can update the Deployment.

## Encrypting and decrypting

- `encryptFor(publicKey, payload, salt?)` encrypts `payload` with the Deployment's key for the holder of `publicKey` and returns an envelope.
- `decryptFrom(publicKey, envelope)` decrypts an envelope that the holder of `publicKey` encrypted for the Deployment's key.
- `salt` is optional. When it is omitted or `null`, a random 16-byte salt is drawn. When it is given, it must be exactly 16 bytes. The salt need not be secret and may repeat: every envelope is encrypted with a fresh random IV.

## What an envelope guarantees

- **Confidentiality and integrity.** Only the two key holders can read an envelope, and any change to it is detected.
- **Direction.** An envelope decrypts only as a message from its sender to its recipient. An envelope a Deployment sent cannot be fed back to it as if the other side had sent it. This does not apply when both keys are the same, for example when a Deployment encrypts for its own key.

An envelope does not provide:

- **Proof to a third party.** Both key holders can derive the same key, so the recipient could produce an envelope that looks as if it came from the sender. If anyone else, including the chain, must be able to verify who produced a message, sign it with the signer's `sign` function.
- **Replay protection.** An envelope that is delivered twice decrypts twice. Put a message ID, counter or timestamp into the payload and check it on receipt.
- **Forward secrecy.** Both keys are long-lived. Anyone who later obtains either private key can decrypt every envelope recorded so far, in both directions. Do not publish envelopes permanently, for example on-chain or on IPFS, if they must stay confidential for the long term, and rotate your own keys.
- **Hiding the payload length.** An envelope is 48 bytes longer than its payload. Pad the payload if its length is sensitive.

## Envelope format

Peers that talk to a Deployment, for example its backend, implement the other side of the scheme:

```
envelope = 0x41 0x43 0x45 0x01 || salt (16 bytes) || iv (12 bytes) || ciphertext || tag (16 bytes)
```

1. **Key agreement.** ECDH on the curve between the sender's private key and the recipient's public key. The shared secret is the 32-byte x-coordinate, leading zero bytes included.
2. **Key derivation.** HKDF-SHA256 over the shared secret, with `salt` and `info = "ECDH " + curve + " AES-256-GCM message" || senderPublicKey || recipientPublicKey`, producing 32 bytes. `curve` is `secp256r1` or `secp256k1`. Both public keys are the 33-byte compressed encodings, the sender's first.
3. **Encryption.** AES-256-GCM with the derived key and a random 12-byte IV, no additional data, 16-byte tag.

### Reference implementation (Node.js)

```javascript
import crypto from 'node:crypto';

const HEADER = Buffer.from([0x41, 0x43, 0x45, 0x01]);

// `ecdh` is your long-term key pair: create it once with crypto.createECDH('prime256v1') or
// crypto.createECDH('secp256k1') and generateKeys(), keep the private key secret, and restore it with setPrivateKey().
// `curve` is the matching name used in the key derivation: 'secp256r1' or 'secp256k1'.
function deriveKey(ecdh, curve, peerPublicKey, salt, senderPublicKey, recipientPublicKey) {
  const sharedSecret = ecdh.computeSecret(peerPublicKey);
  const info = Buffer.concat([Buffer.from(`ECDH ${curve} AES-256-GCM message`), senderPublicKey, recipientPublicKey]);
  return Buffer.from(crypto.hkdfSync('sha256', sharedSecret, salt, info, 32));
}

function requireCompressed(publicKey) {
  if (publicKey.length !== 33 || (publicKey[0] !== 0x02 && publicKey[0] !== 0x03)) {
    throw new Error('Expected a 33-byte compressed public key');
  }
}

// Encrypts `payload` for the Deployment's compressed encryption key `deploymentPublicKey`.
function encryptFor(ecdh, curve, deploymentPublicKey, payload) {
  requireCompressed(deploymentPublicKey);
  const salt = crypto.randomBytes(16);
  const iv = crypto.randomBytes(12);
  const ownPublicKey = ecdh.getPublicKey(null, 'compressed');
  const key = deriveKey(ecdh, curve, deploymentPublicKey, salt, ownPublicKey, deploymentPublicKey);
  const cipher = crypto.createCipheriv('aes-256-gcm', key, iv, { authTagLength: 16 });
  const ciphertext = Buffer.concat([cipher.update(payload), cipher.final()]);
  return Buffer.concat([HEADER, salt, iv, ciphertext, cipher.getAuthTag()]);
}

// Decrypts an envelope that the Deployment encrypted for your key.
function decryptFrom(ecdh, curve, deploymentPublicKey, envelope) {
  requireCompressed(deploymentPublicKey);
  if (envelope.length < 48 || !envelope.subarray(0, 4).equals(HEADER)) {
    throw new Error('Not an envelope');
  }
  const salt = envelope.subarray(4, 20);
  const iv = envelope.subarray(20, 32);
  const ownPublicKey = ecdh.getPublicKey(null, 'compressed');
  const key = deriveKey(ecdh, curve, deploymentPublicKey, salt, deploymentPublicKey, ownPublicKey);
  const decipher = crypto.createDecipheriv('aes-256-gcm', key, iv, { authTagLength: 16 });
  decipher.setAuthTag(envelope.subarray(envelope.length - 16));
  return Buffer.concat([decipher.update(envelope.subarray(32, envelope.length - 16)), decipher.final()]);
}
```

Libraries that return the ECDH shared secret as a big integer (for example `elliptic`'s `derive()`) drop leading zero bytes. Pad it to 32 bytes before the key derivation, or about one key pair in 256 derives a different key.

## Migrating from `encrypt` and `decrypt`

`encrypt` and `decrypt` (Node.js) and `signer_encrypt` and `signer_decrypt` (Cargo) are deprecated. They keep working unchanged, so data encrypted with them stays readable, but they take a caller-chosen salt, produce no envelope and do not bind the direction. To move data a Deployment stored with them, decrypt it with `decrypt` and encrypt it again with `encryptFor`. Switch messages with a peer once the peer implements the envelope format above.
